# Гайд із контриб'юшингу 🚀

Дякуємо за бажання зробити свій внесок у проєкт! Ми раді кожному, хто хоче долучитися до розробки. Цей документ містить основні правила та рекомендації, які допоможуть нам підтримувати якість коду й зроблять спільну роботу комфортнішою.

## 📋 Підготовка до роботи

Перед початком роботи переконайтеся, що ви уважно ознайомилися з цим документом.
Якщо порушуватимете правила командної роботи, на вас чекатиме серйозна розмова.
Жарт. Але правила все одно не порушуйте, а то буде а-та-та! 🤨

Перш ніж розпочати розробку, виконайте команду:

```bash
yarn prepare
```
Вона підготує необхідне середовище для роботи над проєктом.

## 🌿 Найменування гілок

Для найменування гілок використовуйте формат:
`тип/коротка-назва-англійською`

Основні типи гілок:
- `feature/add-login-form` — новий функціонал.
- `fix/header-mobile-padding` — виправлення помилок.
- `docs/update-readme` — зміни в документації.
- `chore/update-deps` — технічні зміни, налаштування та оновлення залежностей.
- `refactor/rework-auth-service` — рефакторинг без зміни зовнішньої поведінки функціоналу.

Назва гілки має бути короткою, зрозумілою та відображати суть змін.
**Важливо:** усі робочі гілки створюються від `dev`, а не від `main` чи інших робочих гілок.

## 💬 Формат комітів

Ми не вимагаємо суворого дотримання конкретного стандарту комітів, проте рекомендуємо дотримуватися кількох простих правил:
- **Мова:** пишіть повідомлення англійською.
- **Чіткість та лаконічність:** коротко описуйте, що саме було зроблено.
- **Зрозумілість:** повідомлення має передавати суть змін без необхідності переглядати весь diff.
- **Атомарність:** розділяйте зміни на логічні коміти. Один коміт — одна завершена зміна або функціональність.

Приклади:
- `Add login form`
- `Fix header mobile padding`
- `Update README`
- `Refactor auth service`

У проєкті ми використовуємо **Yarn Berry (v4.5.0)**. Переконайтеся, що у вас встановлена відповідна версія Yarn.
Нижче наведено основні команди, які можуть знадобитися під час розробки.

| Команда | Опис |
|---|---|

| `yarn start` | Запуск зібраного проєкту. |

|---|---|
| `yarn lint` | Перевірка типів TypeScript та коду ESLint. |

| `yarn lint:fix` | Автоматичне виправлення проблем, які може виправити ESLint. |

### Форматування
| Команда | Опис |
|---|---|
| `yarn format` | Форматування файлів за допомогою Prettier. |

### Підготовка Git Hooks

|---|---|
| `yarn prepare` | Налаштування Git Hooks за допомогою Husky. |

## 🔄 Процес розробки

Дотримуйтеся наступного порядку роботи:

### 1. Створення гілки

Перед початком роботи переконайтеся, що ваша локальна гілка `dev` актуальна.
Створіть нову робочу гілку від `dev`, використовуючи правила найменування, описані вище.
**Це вкрай важливо!** Не починайте розробку від `main` або чужої робочої гілки.

### 2. Розробка та коміти

Внесіть необхідні зміни та створіть коміти.

Для автоматичної перевірки коду використовується Husky. Під час створення коміту він запускає відповідні перевірки, зокрема лінтер і форматування коду.

Намагайтеся дотримуватися єдиного стилю написання коду та не додавайте до комітів зміни, які не стосуються поточної задачі.

### 3. Локальна перевірка

Перед створенням Pull Request обов'язково переконайтеся, що проєкт проходить основні перевірки:

```bash
yarn lint
yarn build
```

Якщо перевірки завершуються з помилками, виправте їх перед створенням PR.

### 4. Створення Pull Request

Після завершення роботи створіть Pull Request у гілку `dev`.

**Назва PR:**

Перед назвою обов'язково вказуйте ключ задачі з Jira.
Формат:
`КЛЮЧ-ЗАДАЧІ Тип: короткий опис`
Приклад:
LF-10 Feat: onboarding`

**Опис PR:**

Заповніть запропонований шаблон Pull Request.
Опис має бути змістовним і зрозумілим. Не обов'язково розписувати все на десять сторінок, але необхідно достатньо детально пояснити:
- Що саме було змінено.
- Які проблеми вирішено або який функціонал додано.
- Як перевірити внесені зміни.
- Чи є додаткові деталі, на які варто звернути увагу рев'юверам.

Якщо зміни стосуються інтерфейсу, за можливості додайте скриншоти.

**Призначення рев'юерів:**

На кожен Pull Request обов'язково призначайте на код-рев'ю **Мирослава та Анну**.

### 5. Код-рев'ю

Після створення PR дочекайтеся фідбеку від призначених рев'юерів.

Не сприймайте зауваження як особисту критику. Мета рев'ю — зробити код кращим, надійнішим і зрозумілішим для всієї команди.

Якщо щось незрозуміло — не соромтеся ставити запитання та обговорювати запропоновані зміни.

### 6. Допрацювання

Якщо рев'ювери залишили зауваження або попросили внести зміни:

1. Виправте проблеми у тій самій робочій гілці.
2. Створіть нові коміти з виправленнями.
3. Переконайтеся, що всі необхідні перевірки проходять.
4. Натисніть **Re-request review**, щоб запросити повторне рев'ю.

Не створюйте новий PR для виправлення зауважень до вже відкритого.

### 7. Злиття Pull Request

**Самостійно зливати власний Pull Request заборонено.**

Злиття PR виконують лише ті учасники команди, які проводили код-рев'ю та погодили зміни.
Самостійне злиття всупереч цьому правилу буде порушенням командного процесу.

> ⚠️ **Важливо:** до статусу «Треба виправити / Needs Fixing» PR можуть переводити лише рев'ювери. Це необхідно для того, щоб статуси Pull Request залишалися зрозумілими та послідовними для всієї команди.

## 👀 Мета код-рев'ю

Код-рев'ю — це **не іспит і не критика розробника**, а спільний процес покращення проєкту.

Ми проводимо його не для того, щоб знайти, до чого причепитися, а щоб зробити продукт якіснішим.

**Для чого ми це робимо:**

- **Якість та надійність.** Виявлення прихованих помилок, граничних випадків і потенційних проблем із продуктивністю до того, як зміни потраплять у production.
- **Обмін знаннями.** Рев'ю допомагає команді розуміти зміни в проєкті, ділитися досвідом і навчатися нових підходів один в одного.
- **Єдиний стиль.** Перевірка відповідності коду архітектурі, загальним домовленостям і гайдлайнам проєкту.
- **Спільна відповідальність.** Кожен учасник команди впливає на якість кінцевого продукту.

> 💡 Будьте відкритими до фідбеку, ставте запитання, якщо щось незрозуміло, та не соромтеся пропонувати власні ідеї!
